# Jev による未決定設計論点の評価

2026-09-29 / model: `jev-1.13.0`

これは相談結果であり、ユーザーの合意・仕様適合性の検証・実装の承認ではない。既存 ADR の決定は変更していない。

## 入力と限界

合意済み設計、責務境界、上流コード調査を state として渡し、24 個の独立した Choice 質問を一括実行した。選択肢は Codex が作成し、すべての質問に「情報不足・他案」を含めた。Jev は理由の文章を生成していない。

規格の必須事項（クライアント認証、対象本人との一致、期限の検証、二重発行防止など）は判断で免除できるものとして扱っていない。SQL 方針や API 設計への回答は、実装・テストによる検証を置き換えない。

選択確率は提示した候補間の分布であり、設計の正しさの確率ではない。confidence は API が別途返した分布集中度の指標。数値による自動採用は行わない。

## 判断が割れた箇所

- public のみ: 52%、情報不足・他案: 47%。以前の短い問い合わせでは public 71% だった。今回は state と選択肢の説明を増やしており、新しい実証結果による変化ではない。
- resolver: 設定必須37%、既存 login 列を既定に31%、情報不足32%。既定動作を支持したとは言い切れない。
- 完了 API の形: 単一メソッド33%、個別メソッド33%、情報不足34%。署名例を比較して判断すべき。
- 完了 API の再送: 同じ結果なら冪等44%、厳密に一度だけ10%、情報不足46%。token endpoint の再利用可否とは別の話。
- 保存期間: アプリが選ぶ46%、情報不足45%。具体的期間は未提示。
- スキーマ・マイグレーション・要求期限は情報不足が最上位。決定に必要な追加情報や具体案が必要。

## Codex の評価（Jev が述べた理由ではない）

次の議論では、選択肢を増やすより、要求受付→本人確認→承認／拒否→poll→消費までの API と状態遷移を一枚の具体案にするのが有用と考える。これにより低確度の完了 API、再送、ID、保存スキーマをまとめて検討できる。

通知引き渡しは callback のみ62%、復旧用の pending request 参照26%。callback のみでは commit と callback の間のプロセス停止を回復できない可能性があるため、採用時にはアプリの durable enqueue または要求の再取得方法を具体化する必要がある。Jev の最上位だけで配送方式を確定しない。

原子的 UPDATE 88% も、DB 間の競合安全性を証明しない。トランザクションの範囲と各 DB の実テストが判断根拠となる。
